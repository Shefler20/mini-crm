# Мини-CRM строительной компании

Веб-приложение для учёта строительных объектов и задач по ним. Постановщик ведёт объекты и задачи, назначает исполнителей и принимает результат. Исполнитель видит только свои задачи и проводит их по рабочему циклу: берёт в работу, отправляет на проверку и возвращает в работу после доработки.

В интерфейсе приложение называется «СтройКонтроль». Вход выполняется по email и паролю. Самостоятельной регистрации нет.

## Технологический стек

- React
- TypeScript
- Vite
- Tailwind CSS
- React Router
- Supabase: аутентификация, PostgreSQL и политики Row Level Security (RLS)
- lucide-react

## Функциональность и роли

Роль хранится в таблице `profiles` и принимает одно из двух значений: `manager` (постановщик) или `executor` (исполнитель). После входа приложение загружает профиль и открывает действия, соответствующие этой роли. Ограничения дополнительно проверяются в PostgreSQL.

### Постановщик (`manager`)

- Просматривает все объекты и все задачи.
- Создаёт, редактирует и удаляет объекты. У объекта есть название и адрес.
- Создаёт, редактирует и удаляет задачи. При редактировании можно изменить название, описание, объект и исполнителя.
- Назначает исполнителем только пользователя с ролью `executor`.
- Просматривает историю изменений задачи: создание, смену статуса, автора записи и комментарий.
- Принимает задачу, которая находится на проверке, или возвращает её на доработку. При возврате комментарий обязателен.

### Исполнитель (`executor`)

- Просматривает объекты, по которым ему назначена хотя бы одна задача.
- Просматривает только свои задачи: в разделе «Мои задачи» и в карточке объекта.
- Открывает карточку своей задачи и видит её историю.
- Переводит новую задачу в работу.
- Отправляет задачу из работы на проверку.
- После доработки снова переводит задачу в работу.

Исполнитель не создаёт и не изменяет объекты и задачи и не меняет статус чужой задачи.

## Жизненный цикл задачи

Новая задача создаётся со статусом «Новая» (`new`). Дальнейшая смена статуса выполняется только функцией `transition_task`.

| Переход | Роль | Условие |
| --- | --- | --- |
| Новая → В работе | Назначенный исполнитель | Задача назначена этому пользователю |
| В работе → На проверке | Назначенный исполнитель | Задача назначена этому пользователю |
| На проверке → Принята | Постановщик | Комментарий не требуется |
| На проверке → На доработке | Постановщик | Комментарий обязателен |
| На доработке → В работе | Назначенный исполнитель | Задача назначена этому пользователю |

Другие переходы функция не разрешает. В частности, из статуса «Принята» выйти нельзя. Комментарий при возврате на доработку проверяется и в интерфейсе, и в PostgreSQL: пустой или состоящий из пробелов текст не принимается.

## Установка и локальный запуск

Нужны установленные Node.js и npm.

```bash
npm install
npm run dev
```

`npm install` устанавливает зависимости. `npm run dev` запускает локальный сервер разработки Vite. Перед запуском нужно настроить Supabase и переменные окружения, иначе клиент не сможет подключиться к проекту.

## Настройка Supabase

1. Создайте проект в [Supabase](https://supabase.com).
2. В настройках проекта скопируйте Project URL и publishable key.
3. В корне репозитория создайте файл `.env.local`.
4. Заполните его по образцу:

```env
VITE_SUPABASE_URL=your_supabase_project_url
VITE_SUPABASE_PUBLISHABLE_KEY=your_supabase_publishable_key
```

Файл `.env.example` — шаблон этих переменных без значений. Секретный ключ `service_role` во frontend не используется. Его нельзя помещать в `.env.local`, в исходный код и в репозиторий: этот ключ обходит RLS.

## Настройка базы данных

SQL-миграции лежат в `supabase/migrations/`. Их нужно выполнить по порядку в Supabase Dashboard → SQL Editor. В репозитории нет конфигурации Supabase CLI, поэтому миграции применяются вручную через редактор SQL.

1. `001_initial_schema.sql` — типы ролей и статусов, таблицы `profiles`, `objects`, `tasks` и `task_history`, индексы и включение RLS.
2. `002_rls_policies.sql` — функция текущей роли, права доступа и первые политики: постановщик управляет объектами и видит профили, исполнитель читает свои задачи и связанные объекты, история доступна только на чтение.
3. `003_task_status_transitions.sql` — функция `transition_task`, которая проверяет роль, назначение и допустимый переход, требует комментарий при возврате на доработку и записывает историю.
4. `004_preserve_task_history.sql` — снимки названия задачи и исполнителя в истории. При удалении задачи связь `task_id` обнуляется, а сама запись истории остаётся.
5. `005_task_assignment_security.sql` — отдельные политики создания, чтения, изменения и удаления задач. Создавать и менять задачи может постановщик, автором становится текущий пользователь, начальный статус — только `new`, исполнителем можно назначить только пользователя с ролью `executor`.
6. `006_task_creation_history.sql` — триггер, который после создания задачи сам добавляет первую запись истории. Клиент эту функцию вызвать не может.
7. `007_history_actor_profiles.sql` — чтение профилей авторов истории для исполнителя. Следующие миграции уточняют это правило.
8. `008_reassigned_task_history.sql` — исполнитель видит историю задачи, которая назначена ему сейчас, и имена участников этой истории.
9. `009_fix_rls_recursion.sql` — вспомогательные функции в схеме `private` и обновлённые политики, чтобы проверки роли, назначения и истории не зацикливались на RLS.

Поздние миграции заменяют часть политик из ранних файлов. После выполнения всей последовательности действует последняя версия правил.

## Создание пользователей

Открытая регистрация отключена: в приложении есть только вход. Учётные записи создаются вручную в Supabase Authentication.

Для каждого пользователя нужна строка в `profiles`. Поле `profiles.id` совпадает с идентификатором пользователя в Supabase Auth: таблица ссылается на `auth.users(id)`. Без такой строки вошедший пользователь увидит сообщение, что профиль не найден.

Пример для SQL Editor, без реальных данных:

```sql
insert into public.profiles (id, full_name, role)
values ('<uuid пользователя из Authentication>', 'Имя сотрудника', 'manager');
```

Для исполнителя в поле `role` укажите `executor`. Тестовые доступы передаются отдельно и в репозиторий не входят.

## Безопасность

Проверка прав выполняется в PostgreSQL. Скрытие кнопок в интерфейсе только повторяет эти правила и само по себе доступ не защищает.

- RLS включён на `profiles`, `objects`, `tasks` и `task_history`.
- Постановщик читает и изменяет объекты и задачи. Исполнитель читает объекты только при наличии назначенной ему задачи и читает только свои задачи.
- Назначить исполнителем можно пользователя с ролью `executor`. Автор новой задачи должен совпадать с текущим пользователем.
- Смена статуса идёт через `transition_task`. Функция проверяет аутентификацию, профиль, роль, назначение и конкретный переход. Для статуса «На доработке» пустой комментарий отклоняется.
- Прямое обновление статуса клиентом закрыто: у роли `authenticated` нет права изменять столбец `status`. Обновление этого поля выполняет функция базы данных.
- История пишется триггером при создании задачи и функцией `transition_task` при смене статуса. У клиента есть только чтение `task_history`; вставка, изменение и удаление записей истории ему не выданы.
- При удалении задачи строки истории сохраняются. В них остаются снимок названия и идентификатор исполнителя, а `task_id` становится пустым.
- Вспомогательные проверки назначения и ролей вынесены в схему `private`, чтобы политики не обходили ограничения рекурсивным чтением тех же таблиц.

## Проверка проекта

```bash
npm run lint
npm run build
```

`npm run lint` запускает ESLint и проверяет исходный код. `npm run build` проверяет TypeScript и собирает приложение для публикации.

## Тестовые данные и проверка ролей

Для проверки используются один постановщик и два исполнителя, несколько строительных объектов и задачи в разных статусах. Так можно отдельно посмотреть полный доступ постановщика и ограниченный доступ каждого исполнителя. Логины и пароли в этот файл не включены: тестовые доступы предоставляются отдельно.
